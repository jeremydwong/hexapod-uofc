Hexapod reachability

PS-6TL-350 · level top frame (roll = pitch = yaw = 0) · generated 2026-10-07. Surge + is front, sway + is right, heave + is up; all distances in mm from home (0, 0, 0).

The question: if we want large surges of about 30 cm, where can we do them, and how fast?
  • Where. From the imitator (exact PS-6TL-350 kinematics): a level 300 mm surge fits with at least 25 mm to spare at both ends anywhere from heave -80 to +90 mm. At home height the surge reach is -306 to +273 mm, so centre the stroke: -167 → +133 mm (about 139 mm spare each end). The most room is at heave -30 mm: -336 to +302 mm (638 mm of travel). Starting from home itself (0) only works forward up to +273 or back to -306, so pre-position for a full 30 cm.
  • How fast. By the tech sheet (surge ≤ 680 mm/s, ≤ 0.66 g), 300 mm cannot take less than 0.55 s (full acceleration, coast at top speed, full braking), or 0.83 s with the smooth S-curve our scripts use. A sensible first fast 300 mm stroke is about 1.2 s (470 mm/s peak, 0.12 g): --rate 470 --max-speed 65535; 1.0 s needs --rate 565 (83% of the speed limit). The imitator executes an instant 300 mm setpoint jump in 0.37 s, faster than the tech sheet allows, and ignores maxSpeed and the acceleration profile: it confirms the commands work, not the robot's real speed.
  • What is still unmeasured. the robot's own reach (safe to measure: paused probe, nothing moves) and its real speed and ramps (must be measured by stepping up --rate on the robot). See section 3.

Names, because they collide

ForceSeatMI
Motion Interface: the vendor's high-level SDK. Sends telemetry or poses to ForceSeatPM, which filters, interpolates (about 250 Hz) and drives the platform. Built for games.
ForceSeatDI
Direct Interface: the low-level SDK we use. Talks straight to the controller; ForceSeatPM must be closed. Licensed per controller.
ForceSeatPM
Platform Manager: the vendor's Windows app (sliders, diagnostics, licence codes).
M10 motion imitator
A small USB box from the vendor that pretends to be a PS-6TL-350 controller: same kinematics and SDK, no motors. Not an API, despite sharing the letters "MI" with ForceSeatMI.
Schematic model
Our own illustrative geometry (the one in the meshcat animations), with leg strokes fitted only to the tech-sheet heave range. Independent of the vendor. Shown here to see how far a guessed geometry is off.

2 · How fast: the imitator at full speed, and what the low-level API offers

Run on the M10 imitator only (uv run hexapod-dynamics refuses any other controller): a 300 mm surge stroke at home height, -167 ↔ +133 mm. First instant setpoint jumps with each acceleration profile and maxSpeed setting, then smooth moves streamed from Python in 1.0, 0.7 and 0.5 s.

Instant step: 0.37 s to within 1 mmSame for all four acceleration profiles and every maxSpeed: the imitator ignores both. About 1.5 m/s peak, over twice the tech sheet's 680 mm/s.
Tilts about 1° in transitAn instant jump moves the six actuators at different rates, so the top frame is not level on the way. Smooth streamed moves tilt less than 0.5°.
Smooth moves track ~30 ms behindThe imitator follows streamed setpoints closely at every speed tried, including 0.5 s (above the robot's speed limit). It does not enforce the tech-sheet limits.
Windows stalls show up as lurchesThe Python sender froze for 65–130 ms several times; each time the command jumped and the platform raced to catch up (below). On the robot this is a jolt. Real-time Linux removes it.

What the low-level API (ForceSeatDI) lets us control

Call / fieldWhat it doesMatters for fast surges because
SendTopTablePosPhyPosition setpoint: sway, surge, heave (mm), roll, pitch, yaw (rad)The only way to command motion. There is no velocity, acceleration or trajectory command: speed comes from how fast we stream setpoints.
maxSpeedSpeed cap, unitless 0–65535 (65535 = none)The imitator ignores it; untested on the robot. Our scripts send 2000 by default; use 65535 for fast moves.
accelerationProfileauto, rapid, balanced, smoothest: shape of the controller's own rampsThe imitator ignores it. On the robot it should change how a setpoint jump is executed.
strategyFullMatch (reject unreachable poses) or BestMatch (move to the nearest reachable one)FullMatch is our safety net near the limits and what the reachability probe uses.
pauseFreeze or release motionEvery paused setpoint is checked but not executed: that is how the probe maps limits without moving.
SendTopTableMatrixPhySame as the pose call, as a 4×4 transformNo speed difference.
SendActuatorsPosLogSix raw actuator setpoints, bypassing the library's kinematics and limit checksNot faster (kinematics take microseconds) and loses the safety check. Avoid.
GetTopTablePosPhy, GetActuatorsPosLog, GetPlatformInfoReported pose, actuator positions and speeds, state bits, errorsOur only feedback. It is computed from actuator positions, not measured on the top frame; record an accelerometer for true onset.
GetPerformanceCountersMicrosecond timings of every SDK callThe tool for measuring send latency on the robot.
…2 variants + FSDI_SFXSmall hardware-generated vibrations (≤100 Hz, ±0.12)Rumble effects, not perturbations.

Not available at all: hardware-timed trajectories, timestamps on commands, a trigger or sync output, or a documented setpoint rate. The vendor's MI manual streams positions every 4 ms (250 Hz), which suggests the controller consumes setpoints at about that rate.

3 · The robot itself

Not measured yet. Two steps, in this order:

  1. Reach (safe, nothing moves): ForceSeatPM closed, then uv run hexapod-envelope --ip 10.1.1.75 --heave-step 5 --output output/reachability/robot.json, then rebuild this report. Every probe command is paused; the platform does not move. It adds the robot as a third shape and confirms the imitator's limits.
  2. Speed (the platform moves): do not use hexapod-dynamics on the robot. Step up the 300 mm stroke with hexapod-park-test --max-speed 65535 and --rate 100 → 235 → 340 → 470, checking each report for lag, overshoot and lurches before going faster. Add a top-frame accelerometer for true onset times.

Method and caveats

  • Reachability: at each height (5 mm steps), 72 directions in the sway/surge plane, binary search to 1 mm for the furthest pose the vendor library accepts with FullMatch. Every probe command is paused; nothing moves. The outline assumes the region is star-shaped around home. On the imitator the full probe takes about 3 s, because the check runs in the vendor library on the PC.
  • Imitator speeds: reported pose polled every ~2 ms while the setpoint is re-sent every 10 ms; positions median-filtered, then differentiated with 21 ms (speed) and 41 ms (acceleration) smoothing.
  • The imitator reproduces the PS-6TL-350's kinematics exactly (home-height limits match the tech sheet to 0.5 mm) but not its dynamics: it ignores maxSpeed and the acceleration profile, and moves faster than the tech sheet allows.
  • Kinematic reach is not usable reach: payload, speed, controller software limits and safety margins all shrink it. Keep 25 mm or more from the edge.
